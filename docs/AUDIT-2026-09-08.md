# SUPSERV ERP — audit and repair plan

**Date:** 8 September 2026 · **Scope:** the whole repository at `C:\SUPSERV-ERP` — 90 routes, 24 schema files, 123 test files, 1 608 passing tests.

---

## The verdict

The ERP is not half-built. It is **built and unwired**.

Nearly every complaint traces to the same shape: a domain function that works, is tested, and has no button; a database column that is migrated, read, and never written; a component that was designed for exactly this problem and has zero consumers. The logic is there. The seam between the logic and the screen is missing.

Five proofs, each verified by grep:

| What exists | What it lacks |
|---|---|
| `makeTender()` — turns an enquiry into a tender, seeds its folder, writes the audit entry, `src/domain/tender/store.ts:235` | **Zero callers outside `tests/`.** No route, no form, no button. A tender cannot be created through the interface at all. |
| `deal.deleted_at` — migrated (0015), and `listDeals` already filters `isNull(deal.deletedAt)` | **No writer anywhere in `src`.** The read side is finished; nothing can set it. |
| `RulePopover` — the component that makes every grey button explain itself | **Imported by zero files.** |
| `StateBlock` — an empty-state block with an `action` slot for the next step | Used **twice**, both of them error screens. ~60 empty states render as a bare paragraph. |
| `DataTable` + filters + saved views + pagination + bulk bar | Used by **4** files. **53** other files write a raw `<table>`. |

That is the good news. Most of the repair is wiring, not building — and the wiring is cheap because the hard part (the rules, the money, the state derivation, the document engine) is done and proven.

The bad news is that the unwiring is systematic enough that the system currently cannot do the one thing it exists for: turn an email into money. Every link in that chain has a break.

## 1. An RFQ arrives and nobody can read it — not you, not the ERP

You are right, and it is worse than you think: there are **five** independent breaks in this one chain.

**a. The bytes are never fetched.** `src/capture/mail/graph.ts:180-188` asks Microsoft Graph for attachments with `$select=id,name,contentType,size,isInline`. No `contentBytes`, no `/$value`. Filenames and sizes arrive. Content never does.

**b. Nothing writes `storage_path`.** `src/domain/intake/mailbox.ts:209-219` inserts one `intake_attachment` row per file with `storagePath` left null. The column is *read* in three places and *written* in none. So every attachment's state is permanently `absent`.

**c. The file server refuses.** `src/app/api/files/[id]/route.ts:60-65` returns `409 bytesNotHere` when `storagePath` is null — which is every email attachment, forever.

**d. The screen does not even offer a link.** `src/app/[locale]/(app)/inbox/[id]/page.tsx:196-224` lists attachments as plain `<li>` rows: a paperclip, the filename, and the text "in Outlook only". There is no `<a>` in that block at all — not even in the branch where a storage path exists. The only escape is "Open in Outlook".

**e. There is no ZIP code in the repository.** A repo-wide grep for `zip|unzip|jszip|yauzl|adm-zip|archiver|decompress` outside `node_modules` finds three things: a backup script, a line in the runbook, and one translation string on the Channels screen that *advertises* ZIP support. A `dossier.zip` today produces exactly one opaque row and nothing else, ever.

And two more, downstream:

**f. Text extraction is PDF-only.** `src/capture/ocr/provider.ts:100-119` handles `application/pdf` and throws `NeedsOcr` for everything else — including PNG and JPEG. DOCX and XLSX are not readable at all, though `exceljs` is already a dependency. The OCR container has a `Dockerfile` and a compose service, but there is **no `ocr/` directory and no server code**; `OCR_URL` sits in `.env` read by nothing.

**g. The review screen shows text, not the document.** `/inbox/dossier/[id]/review` renders stored page text with the quote highlighted. Law 2 asks a person to confirm a field *against the source*, and the source is not on screen. Meanwhile `documents/[id]/page.tsx:220-232` already does this correctly, with the browser's own viewer and no new dependency:

```tsx
<object data={`/api/documents/${id}/pdf`} type="application/pdf" className="h-[900px] w-full" />
```

**One thing is already half-wired for you.** `ingestPdf()` in `src/domain/intake/dossier.ts:29` already accepts `messageId` and `attachmentId`, and `intake_dossier` already has both foreign-key columns. No caller passes them. That is the email → dossier bridge, waiting for one argument.

## 2. The deal is created empty, and there is nothing to do next

**Empty on purpose, and it stays empty.** `src/domain/intake/commit.ts:221-228` explicitly leaves `clientReference: null`, `submissionMethod: "unknown"`, `expectedValue: null`, `clientInstructions: null` and zero lines, with a comment saying so. What it fills is the party, the subject line, the contact, the received date and an unconfirmed deadline. That is correct behaviour under Law 2 — but only if something later reads the attachment. Nothing does, so "later" never arrives.

**The deal cannot see where it came from.** `deal.intake_message_id` is written and read by no screen. `deals/[id]/page.tsx` contains no reference to the inbox, the message, the attachments or the dossier.

**Confirmed extractions go nowhere.** `src/domain/intake/extract.ts` already proposes six tender fields with citations — submission deadline, opening session, place of deposit, bid bond, offer validity, late penalty. A person confirms them, they land in `extraction_field`, and **`intake_dossier` has no `deal_id`**. The confirmation is stored and never reaches a deal.

Correspondingly, `deal.requiredValidityDays`, `deal.requiredDeliveryDays` and `deal.latePenalty` are read by the supplier-conflict checks (`sourcing-store.ts:268-270`) and by the offer validity check (`offer/submit.ts:120`), and **written by no screen at all**. Those checks are permanently silent.

**And the page gives no order of operations.** The deal detail renders eight independent cards at once — requested items, decision, instructions, details, mark lost, ask suppliers, build offer, project — with no sequence, no completion state, and two `primary` buttons in unrelated cards. There is no stepper, no checklist, no "what now".

This is the direct answer to *"which steps?"*: the software never says.

## 3. An RFQ cannot become a tender — and the function to do it already exists

`makeTender()` is written, transactional, guarded against double-conversion, seeds `tender_piece` from the procedure, and writes an audit entry naming screen 07. It is exercised by three integration test files. **Nothing under `src/app` imports it.** There is no `/tenders/new`, no `actions.ts` under `tenders/[id]`, and no create button on the tenders list.

So `/tenders` is structurally empty forever, and its own empty state tells you to do something impossible:

> "No tenders yet. A tender is an enquiry answering a formal procedure — open the enquiry and record the procedure, the place of deposit and the bid bond, and it appears here with its folder."

There is no such form. `bidBond` has zero write sites in `src/app`. `submissionMethod` can only be set once, at `/deals/new`, and is read-only afterwards — there is no `/deals/[id]/edit`.

Also unreachable, all exported and all with no UI: `saveCredential` (so your CNAS/CASNOS expiry dates cannot be entered, so every folder piece computes as `missing` forever), `recordCaution`, `markSubmitted`, `addPiece`, `removePiece`. The tender detail page has no form and no actions at all. `/tenders/[id]/bpu` — the hardest screen in the codebase — is linked from nowhere except itself.

**Your mental model is already in the schema.** `tender.procedure` is one of `aonr | aoo | consultation | rfq | gre_a_gre`, and `seedFor(procedure)` in `src/domain/tender/pieces.ts:93` already drops the caution, the qualification and the casier judiciaire for `rfq` and `consultation`. "A simple RFQ" and "a tender" are one model with two seeds. The distinction you make in your head is expressible today, with a select box and one server action.

**The classifier already guesses, and the guess is thrown away.** `src/domain/intake/channels.ts:121` seeds a routing rule matching *consultation*, *avis*, *appel d'offres*. `mailbox.ts:32` tags attachments matching `cahier|charges|cctp|dossier|appel` as `tender_dossier`. And `commitEnquiry` reduces all of it to `source: "tender"` — a string nothing reads. No tender row is created.

Signals available and unused: ZIP present, attachment count, page count, *soumission*, *bordereau*, *BPU*, *DQE*.

## 4. Nothing can be removed, and nothing explains why

**The soft-delete machinery covers exactly one entity: companies.** `src/domain/deletion.ts` implements `discardParty` / `restoreParty` / `archiveParty` / `listBin`, all of them on `party` only. `records.delete` is checked in exactly one file in the whole app — `companies/delete-actions.ts:20`.

**A deal cannot be removed.** The column is migrated, the list already filters on it, nothing writes it. `deals/[id]/actions.ts` exports three actions: decide, lost, reopen. Marking junk "lost" does not help — the default deals list is *All*, so a lost deal keeps its row with a red badge forever.

**A draft invoice cannot be deleted.** `document` has **no `deleted_at` column at all**, in the schema or any migration. `documents/[id]/actions.ts` exports `issueDocument` and `fileIssuedDocument`, nothing else. Deleting a never-issued draft — no number allocated, no series consumed, `locked_at` null — is the one removal that is unambiguously safe under Law 5, and it is the biggest gap.

**An issued invoice cannot be cancelled.** `invoices.cancel` is declared in `PERMISSIONS`, granted to `gerant`, and referenced exactly once in the codebase: its own declaration. `document.status` documents `credited`, `credit_note` is a real kind — and no avoir flow exists. CLAUDE.md's acceptance test 3 ("issue three, cancel the second, issue a fourth") cannot pass today.

**It is not a permission problem.** `src/auth/session.ts:49-54` bootstraps the first person to sign in as `gerant`, and `ROLES.gerant` is every permission. You hold `records.delete` and `invoices.cancel` and still cannot act.

**The worst part is the silence.** `Button` has a `disabledReason` prop, deliberately implemented with `aria-disabled` rather than `disabled` "so nobody could ever read the reason it is grey". It is used correctly for issue and send. For deletion there is no button, no grey button, and no explanation — just absence. That is exactly the discomfort you describe.

Two aggravations: the four bulk actions on the deals list are literal no-ops (`run: () => {}`), so ticking rows and clicking does nothing, silently. And there is no reset path — no `db:reset` script, no wipe procedure in the runbook. Every junk row you typed is permanent.

## 5. Ninety pages, four competing homes, twenty screens with no main action

**The rail is 24 rows.** `docs/UI_INDEX.md` specified 18 and said so explicitly. The sidebar's own comment concedes the overflow: *"Twenty-four destinations do not fit in the 768 pixels of a 12-inch laptop."* The fix applied was a scrollbar.

**24 of 88 in-app screens are one click from the nav. The other 64 are not.** Fully unreachable by clicking: `/settings/modules` and `/settings/forms` — two screens whose entire purpose is to make a gap visible, hidden. Reachable only from the phone bar, never on a laptop: `/approvals` and `/prices/new`. Reachable only from inside its own subtree: `/tenders/[id]/bpu`. Orphaned: `/deals/[id]/items`.

**You land on the wrong screen.** `src/app/[locale]/page.tsx` redirects to `/deals` — a pipeline list. One row above it in the nav sits `/today`, which is the best-designed surface in the entire application: four ordered bands, nine item kinds, each with a minute estimate and a link to the exact screen where the work happens, all computed from existing rows with no task table. It is not the landing page. `/dashboard`, `/week` and `/waiting-on` are three more competing answers to the same question.

**Twenty screens have zero primary action** — including every WORK nav item except Projects: Tenders, Sourcing, Offers, Orders, Deliveries, and also Payments, Compliance, Files, Conversations, Waiting on, Week, Today, Dashboard, Search, Reports.

**One concept, three names.** The nav says *Deals*, the route is `/deals`, the French is *Affaires*, and the English body copy says **enquiry** 178 times against 54 for *deal*. The app tells you to "open the enquiry" and there is no Enquiries anywhere on screen. Similar drift: *Projects* for *Chantiers* (a travaux SARL says sites/works), *Sourcing* for *Approvisionnement*, *Payments* for *Règlements* while `/payments/ageing` is *relances*.

## What is genuinely good, and must survive the repair

This is a well-built codebase. The repair must not damage these:

1. **Computed state, never stored state.** Overdue, won, paid, delivered, the tender folder percentage, the setup progress — all derived. Applied consistently, and it is the strongest idea in the system.
2. **`/setup` (screen 85).** Eleven computed steps, numbered, blocking ones with a filled badge and a primary button, done ones with a green badge and no button, and a banner naming exactly what is missing. This is the pattern that answers "which steps?" — and it already works.
3. **`/today`'s `gather()`.** Five queries, four ordered bands, nine kinds, each with an href and an estimate. Not one row is a todo.
4. **`/settings` as a state hub** — every row shows a live count and routes to the one page that owns that data.
5. **Honest refusals with a route** — `NotDiscardable`, `?blocked=issued`, `deletedPartyNotice` ("never a blank 404, say what used to be here"), the setup banner naming the four missing fields.
6. **The `DataTable` system** — filters, saved views, pagination, columns, bulk bar. Complete. Needs adopting, not rebuilding.
7. **47 dated decision records.** Almost every surprising choice has a written reason. That is why this audit could be precise.
8. **The mobile rule** — capture and approve on the phone, build and decide on the laptop — encoded as data with a unit test.

## What not to do

These are traps this codebase has already avoided, and the repair must not walk into them:

- **Do not add a `stage` column to `deal`.** Law 1. The stage is computed from documents and it is correct. Same for any status you are tempted to keep true with a cron job.
- **Do not add a `task` table.** `/today` is built on the principle that a task is a fact somewhere else, plus the `note` table for the one thing the system never saw. Adding tasks would create a second truth to maintain by hand.
- **Do not loosen `RENDERABLE`** in `src/domain/files/serving.ts` to make DOCX or HTML display inline. Inline HTML from anyone who can email `contact@` is stored XSS; SVG is excluded for the same reason. A ZIP-extracted HTML file must not become renderable. Convert, don't serve.
- **Do not reach for a cloud OCR or conversion API.** CLAUDE.md: nothing in this system requires a paid service, and `docs/OCR.md` already rejected the M365 route on that ground.
- **Do not build a second PDF renderer.** Law 3 — one document engine. A DOCX preview path must not become one.
- **Do not hard-DELETE anything**, and do not let a deal's discard take an issued invoice with it — migration 0016 set `document.deal_id` to `ON DELETE no action` for exactly that reason.
- **Do not give the assistant a delete tool.** Law 6, and there is a unit test asserting it.
- **Do not write a third table component.**

## Where to start, concretely

If you only do three things this week:

1. **0.7** — change the landing route to `/today`. One line. It changes what the system is *for* every morning.
2. **0.1 + 0.2** — draft-document discard and deal discard. Two days, and the junk stops accumulating.
3. **1.1 + 1.2 + 1.5** — fetch the bytes, store them, show a viewer. This is the shortest path from "the ERP is blind" to "I can read the RFQ inside the ERP", and everything downstream — extraction, tender detection, auto-filled deadlines — is blocked behind it.

Wave 1 as a whole is the one that decides whether this ERP is worth using. Everything else is comfort and clarity; that one is capability.
